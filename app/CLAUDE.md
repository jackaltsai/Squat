# 深蹲智慧健身輔助系統 — 專案開發計畫

> 本文件對應論文《基於影像姿態辨識之深蹲智慧健身輔助系統設計與評估框架》，
> 作為 Claude Code 在此專案中的開發上下文。請依照下方里程碑順序開發，
> 每個里程碑完成後標記狀態並提交一次 commit。

## 專案概述

- **目標平台**：Android（Kotlin + Jetpack Compose）
- **核心技術**：CameraX（影像串流）+ Google ML Kit Pose Detection（骨架辨識）
- **系統架構**：感知層 → 數據處理層 → 核心邏輯層 → 輸出應用層
- **最低 SDK**：建議 API 24+（CameraX 與 ML Kit Pose Detection 相容需求）

## 技術棧

```
語言: Kotlin
UI: Jetpack Compose
相機: androidx.camera:camera-camera2 / camera-lifecycle / camera-view (1.4.0)
姿態辨識: com.google.mlkit:pose-detection:18.0.0-beta5
本地儲存: Room
語音: Android TextToSpeech
```

## 開發注意事項

1. **座標系統**：ML Kit 回傳的關鍵點座標會依裝置方向與鏡頭方向（前/後鏡頭）而異，M1 階段務必先確認座標轉換正確，否則後續髖部「上升/下降」方向判斷會相反。
2. **效能**：`ImageAnalysis` 使用 `STRATEGY_KEEP_ONLY_LATEST` 避免堆積幀造成延遲。
3. **隱私**：不儲存原始影像/人臉畫面，僅儲存骨架關鍵點與統計數據（對應論文 4.3 節倫理規劃）。
4. **可重現性**：所有門檻參數（信心度閾值、EMA alpha、狀態機穩定幀數、深度分級門檻）都應集中放在一個 `Config` 檔案，方便之後 M5 階段調參與記錄實驗版本。

## M6｜訓練統計（本機日／週／月）

**目標**：讓使用者看到自己的累積訓練量，並為後續多動作支援預留資料結構。

### 任務清單
- [x] `SquatRepRecord` 新增 `exerciseType` 欄位，Room v2 → v3（`ALTER TABLE ... DEFAULT 'SQUAT'`，既有紀錄全是深蹲，回填值語意正確）
  - 先加欄位而非等到真的有第二種動作，是為了少做一次 migration —— 每次遷移都是一次讓測試人員資料消失的機會
- [x] `SquatRepDao` 新增 `recordsSince` / `countBetween` / `totalCount` / `earliestTimestamp`
- [x] `stats/TrainingStats.kt`：日期分桶純函式（`DateBuckets`、`buildDailyBuckets`）
- [x] `stats/TrainingStatsOverlay.kt`：今日／本週／本月三個大數字 + 最近 14 天長條圖 + 每日明細
- [x] 進入點：選擇訓練模式畫面的「訓練統計」
- [x] 單元測試 `app/src/test/.../TrainingStatsTest.kt`（純 JVM，`./gradlew test` 可跑）

### 設計決策

1. **日期分組在 Kotlin 做，不用 SQL 的 `strftime`**
   `strftime('localtime')` 取的是查詢當下的裝置時區，而摘要數字的區間邊界是 Kotlin 算的。
   兩套時區邏輯並存時，跨日跨月的那幾筆會在「摘要」與「每日明細」之間對不起來。

2. **用 `java.util.Calendar` 而非 `java.time`**
   minSdk 24，`java.time` 需要 API 26。不開 core library desugaring 的前提下 Calendar 是唯一選擇。

3. **一週從星期一起算**
   zh-TW locale 的 Calendar 預設 `firstDayOfWeek` 是星期日，與一般人講「這週」的理解不符，因此明確指定。

4. **長條圖以「期間內單日最高」為滿格**
   固定上限會讓訓練量少的使用者整排都是貼地短柱，看不出相對變化。

5. **沒訓練的日子也畫出空格**
   少了空白格，圖表會把「連續練三天」與「三天裡只練一天」畫成一樣。

### 驗收標準
覆蓋安裝舊版後，既有紀錄的 `exerciseType` 全部為 `SQUAT` 且筆數不變；統計頁的今日／本週／本月數字與每日明細加總一致。

依「風險遞增、相依性遞減」排序：

1. ~~統計頁 + `exerciseType` 欄位~~ ✅ 即 M6
2. **動作抽象層 + 品質檢查重構**
   ⚠️ `PoseQuality.passesQualityCheck` 目前要求 `KeyPointType.entries` **全部**到齊。
   若把 enum 從 6 個擴到 33 個全身關鍵點，這行會要求 33 點全部偵測到且信心值達標，
   結果是幾乎每一幀都被丟棄、App 表面上完全沒反應。
   必須改成每個動作宣告自己需要哪些關鍵點。
3. **坐站（Sit-to-Stand）**
   Senior Fitness Test 的 30 秒坐站測試，有臨床常模；軌跡同為髖部垂直位移可複用狀態機；
   椅子在身後等於安全網，是最適合長者的第一個新動作。
4. **全身偵測**
   ML Kit 本來就計算全部 33 個點，`PoseAnalyzer.landmarksOfInterest` 只是挑了 6 個，
   所以開啟全身**不增加推論成本**，成本在上面第 2 點的重構。
5. **卡路里估算**
   MET 公式需要體重（新增個資輸入），且族群平均的個體誤差達 ±20~30%。
   純本機儲存不算 Play 定義的 collection，但隱私權政策需補充說明。
   **不可列入論文量化指標** —— 這是 UX 功能，不是研究數據。

### 長者取向的安全性提醒
現有 L1/L2/L3 是「挑戰更深」的框架。使用者換成長者後，鼓勵多做一下或蹲更深都有致傷風險，

原規劃九個動作，涵蓋三種計量範式。**已縮減為六個，全部是次數型。**
移除的三個：側身伸展、單腳站立（持續型，計秒）、30秒坐站 STST（限時計次）。

隨之刪除的抽象：

### 坐站練習（`CHAIR_SQUAT`）✅ 已實作（2026-10-01，**尚未上實機**）

坐站與深蹲共用同一個 `SquatStateMachine` —— 軌跡同為髖部垂直位移，深度本來就用
使用者自己的 `Duser` 正規化，椅面只是把深度限制住，不需要另一套邏輯。

**但舊的轉折判據必須修掉，否則坐站會壞。** 原本是：

```kotlin
risingFrameCount = if (prev != null && hipY < prev) risingFrameCount + 1 else 0
```

要求「連續 3 幀嚴格比上一幀高」。連續動作的深蹲沒問題，坐站有兩個情境會打壞它：

| 情境 | 舊判據的結果 |
|---|---|
| **長輩慢速起身**（每幀位移接近雜訊量級） | 只要一幀沒嚴格上升計數就歸零，永遠湊不到 3 幀連續 → **停在 DOWN，整下不計次** |
| **坐在椅面上停頓**（髖高是平的） | 隨機雜訊遲早湊出 3 幀連續「下降」 → **人還坐著就誤觸發最低點** |

改成以 `Config.TURN_CONFIRM_RISE_RATIO`（0.03）判斷「**已從本次最低點回升多少**」：
判據與速度無關，停頓時回升量為 0 也不會誤觸發。這仍然是論文第 7 節要求的
「轉折點 + 連續幀確認」，不是單一高度閾值 —— 比較基準是本次動作實際到達的最低點。

`lastBottomDepthRatio` 取的仍是 `peakHipYInDown`（下降過程的最低點），
與轉折何時被確認無關，**所以這個改動不會改變 p 值的語意**，既有資料仍可比較。

- [x] `SquatStateMachine` 轉折判據改為回升量（深蹲行為不變，有迴歸測試保護）
- [x] 校正語音改用動作名稱：坐站時會說「請完成兩次**坐站練習**」而非「兩次深蹲」

#### `RepSignal`：讓狀態機不知道自己在數什麼
新增 `squat/RepSignal.kt`。動作把一幀關鍵點換算成單一「進度」純量
（**0 = 站姿靜止，正值 = 往動作方向前進**），並自己宣告判準與三個門檻。
深蹲往下、舉手往上，在這個抽象下都是「進度變大再變小」，
所以五階段狀態機只需要一份，`SquatStateMachine` 完全不含動作知識。

- `SquatSignal` —— 進度 = 髖部下降量 / 髖踝距離，門檻沿用 M2 實測調過的絕對值，
  **行為與抽象化之前完全相同**（四個深蹲迴歸測試即為此而存在）
- `ArmRaiseSignal` —— 進度 = 手腕上舉量 / **校正時的**肩寬
- `StandCalibrator` —— 站姿校正要量什麼由動作決定。不能統一累加髖踝肩腕四組：
  品質檢查只保證當前動作需要的點到齊，手臂動作時髖與踝可能根本沒偵測到，
  一起累加會讓站姿校正**永遠跑不完**

#### `CalibrationKind` 已刪除，改由 `RepSignal.target` 唯一決定
`target == null`（深蹲家族）代表分母是個人化 `Duser`、需要兩下基準校正；
非 null 代表判準是固定解剖學地標、站姿校正就取得了分母。
同一件事只記在一處，才不會像那個欄位一樣悄悄失去同步。

#### 雙臂高舉的判準是「舉到肩高」
`target` = 站姿時手腕低於肩的距離 ÷ 肩寬（實測身體比例約 **2.14 個肩寬**）。
手腕剛好在肩線時 `p = 1.0`。這同時是個人化的（用使用者自己的站姿與肩寬量）
又是絕對的（錨在肩線，不是錨在一次試探性的基準動作）。

對長者而言這比個人化門檻更安全：**舉手過肩本來就有解剖學標準，不該因人放寬。**
入門門檻 p ≥ 0.90 代表舉到肩高的九成即達標，`safetyNote` 也已寫明
「肩膀會痛就降低高度，不必舉到頂」。

用**校正時的**肩寬而非逐幀肩寬：使用者稍微側身時逐幀肩寬會縮小，
比值被放大、憑空多出達成率。固定用校正值與 M3 的設計一致。

三個門檻取 `target` 的比例而非絕對值 —— 手臂進度量級約 2 個肩寬，
深蹲約 0.3 個腿長，差一個數量級，沿用深蹲絕對門檻會過度靈敏。

#### 站姿校正失敗必須說話
若使用者在站姿校正時就把手舉著，手腕沒有低於肩、判準會是 0 或負數。
`ArmRaiseStandCalibrator.build()` 回傳 null，流程**重新倒數並顯示＋念出「請雙手自然下垂」**。
不處理的話畫面會停在「數到 0 卻什麼都沒發生」，使用者只會以為程式壞了。

#### 框位引導依動作分流
上肢動作改用：肩與腕要在框內、**肩膀上方要留得下舉起的手**、遠近用肩寬佔畫面寬度判斷。
新增 `MISSING_WRIST`（請讓雙手入鏡）、`NO_HEADROOM`（請往後站）。

  我在測試裡假設 2.14 估太高，但門檻取 target 比例會自動縮放，不是 bug
- p 值確實有鑑別力：1.81 / 1.67 / 1.70（舉過肩，GREEN）、1.03（剛好到肩高，GREEN）、
  0.69 × 2（只舉到七成，RED）

❌ **但每下之間隔了 18~47 秒**（正常應 3~5 秒），使用者回報「距離很難拿捏」。
原因是我加的 `FRAMING_SHOULDER_HEADROOM_RATIO = 0.30`（肩膀上方要留得下整隻舉直的手）：

| 距離 | 肩 Y / 畫面高 | 門檻 0.30 | 肩寬 / 畫面寬 | 遠近判定 |
|---|---|---|---|---|
| 2.0 m | 0.241 | ✗ 請往後站 | 0.317 | OK |
| 2.5 m | 0.291 | ✗ 請往後站 | 0.253 | OK |
| 3.0 m | 0.325 | ✓ | 0.211 | 快被判太遠 |
| 4.0 m | 0.370 | ✓ | 0.158 | 太遠 |

「請往後站」（沒頭頂空間）與「請往前站」（太遠）互相拉扯，距離當然拿不準。
**更根本的錯誤：站立 1.70m、雙手舉直約 2.20m，「全身入鏡」與「舉直的手也入鏡」
在物理上無法同時成立。** 那條檢查從一開始就不可能滿足。

而使用者的資料正好反證了它的必要性 —— p = 1.8 代表手腕**確實被追蹤到遠高於肩**。
那條檢查不是在保護使用者，是在擋使用者。

**修正：移除該檢查。** 判準既然是「舉到肩高」（p = 1.0），就只需要追蹤到肩高，
不需要整隻手入鏡。只保留「手腕貼齊畫面上緣」的提醒（門檻 0.03 → 0.06，
提早一點出聲），訊息改為 **「舉到肩膀就好」** 而不是「請往後站」——
使用者正在動作中，叫他停下來走過去重新站位，不如直接告訴他舉到哪裡就夠。
`ARM_RAISE.guidance` 一併改為「雙臂向上舉起再放下，舉到肩膀高度就夠。」

`FramingGuidanceTest` 新增一條「全身入鏡時肩膀位置偏高仍視為框位良好」鎖住它不被加回來。
